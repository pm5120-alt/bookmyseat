# Assumptions and business rules

- The SQLite database bundled with the supplied project is the legacy dataset to preserve. No external database was accessed. The untouched snapshot and pre-Phase-2 working checkpoint are retained locally outside the submission archive. Neither operational database nor checkpoint is distributed.
- Legacy `Theater` rows and their movie/time columns remain. New `Screen`, `Show`, and `ShowSeat` records represent scheduled inventory. Migration `0007` maps legacy seats to the theater's first screen, creating `Screen 1` only if that theater has seats but no screen. It does not delete or renumber seats or reservations.
- Existing bookings have no captured-payment evidence. They remain historical records but do not qualify for paid/verified-viewer review eligibility.
- Verified-viewer eligibility means captured payment plus confirmed booking for a show whose scheduled start plus movie duration has passed. This cannot prove physical attendance.
- A hold is 120 seconds by default (`SEAT_HOLD_SECONDS`; the older `BOOKING_HOLD_SECONDS` env name is still accepted as an alias) and can be configured by environment. Expired holds are rejected during confirmation and released by cleanup/recovery work.
- Cancellation policy: an unpaid pending booking can be cancelled before its show starts and releases its seats. A confirmed paid booking can request a full refund before show start. It remains confirmed and its seats remain unavailable while provider refund status is requested, pending, failed, or unknown. Seats are released only after verified refund completion. Unknown outcomes require retry or manual reconciliation; the UI/model must not claim refunded. Cancellation after show start is rejected.
- Refunds are modeled as full amount; a provider-reported partial refund is marked for review rather than treated as a completed full refund. Duplicate-charge and late-payment paths are tracked separately from the original booking and require refund or manual recovery.
- Payment integration targets Razorpay INR. Test Mode credentials exist only in the local ignored `.env`. In the 2026-10-24 browser check, order creation returned HTTP 200 and opened Razorpay Test Mode Checkout, which displayed “No appropriate payment method found.” No payment was completed; provider payment, webhook and refund flows remain unverified.
- PostgreSQL is required for meaningful row-lock and concurrent reservation evidence. SQLite unit tests do not establish PostgreSQL behavior.
- Celery and Redis are separate services. Failed dispatch should be discoverable by recovery scans. The local suite invokes task functions directly; a real broker/worker/beat run remains outstanding.
- Tickets are stored privately and accessed through owner-checked routes. External object storage and production media retention are not configured.
- User booking history is complete, user-scoped and paginated at 20 records per page. Recently viewed movie history is capped at 30 per user. Recommendation ranking awards two points per overlapping genre and one point per overlapping language; it excludes already-booked titles and titles without an active upcoming show, then falls back to recent trending movies when there is no useful match.
- No default administrator account or password is created. For an owner-controlled installation, use `createsuperuser`. For an assignment/demo environment, run `python manage.py create_demo_admin`; the account is `demo_admin`, a non-superuser staff user with only `movies.view_booking_analytics` via the clearly labelled `BookMySeat Demo Administrators` group. Supply `BOOKMYSEAT_DEMO_ADMIN_PASSWORD` for that demo environment or let the command generate and display a password once. Existing `demo_admin` accounts are never reset or modified. Never store the selected/generated demo credential in source control or production settings.
